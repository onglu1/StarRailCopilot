# 差分宇宙识别流程与性能

## 一帧如何处理

1. 使用配置选定的 SRC 原生截图方式获取 1280×720 画面，沿用原生采样间隔。实际后端以各配置的 ScreenshotMethod 和启动日志为准。
2. 先用小范围模板判断地图 HUD；其他页面读取标题条，识别祝福、方程、奇迹、事件等页面。
3. 根据页面类型裁剪必要区域。选择页面只读卡名，用图形匹配判断未收录、推荐与星级，不识别整段卡片说明。
4. 按「未收录 > 系统推荐 > 等级 > 自定义同级偏好」选择。新卡片仍须跨帧确认稳定，不能为了速度选择尚未显示完的标记。
5. 点击交给 SRC 原生控制，继续读取新截图确认菜单、按钮或结果发生变化。结束菜单及结束确认框分别检测，禁止凭旧画面反复返回。

截图大小与 OCR 范围是两回事。裁剪发生在 OCR/模板匹配之前；缩小截图输出会影响 SRC 的坐标和原生素材，因此保留原始分辨率。此前独立只读 MuMu IPC 抓图测试约 7–8 ms，该数字不能代表其他截图后端的耗时，实际瓶颈以生产进程采样和整轮日志为准。

## 主要识别区域（1280×720）

| 内容 | 区域像素范围 | 说明 |
|---|---|---|
| 左上页面标题 | x=70–467，y=33–69 | 单行识别；识别不到再检查中央标题和上方标题带 |
| 普通卡名 | x=102–1229，y=302–360 | 只检测卡名条，不扫描说明正文 |
| 奇迹卡名 | x=102–1229，y=353–396 | 与普通卡分开 |
| 未收录/推荐 | 检测到的卡片上方约三分之一，加20px边距 | 无法定位卡片时才使用原有回退范围 |
| 选择确认 | x=934–1242，y=605–684 | 特殊居中按钮回退到 y=598–691 的底栏，不再扫描下方整片区域 |
| 入口开始按钮 | x=896–1126，y=605–677 | 不再识别整个下三分之一 |
| 常见探索结果标题 | x=90–358，y=216–288 | 星阶提升等不同布局继续保留原范围回退 |
| 地图目标 | 依实际门/事件牌可出现的视野范围 | 保留必要搜索范围，采用缩放候选、原尺寸验证和同帧缓存 |

所有 DU 的归一化识别范围必须满足 `0 ≤ x1 < x2 ≤ 1`、`0 ≤ y1 < y2 ≤ 1`，非法范围直接报错。动态标记区域按图像边界限制。

同一帧复用 OCR 和模板匹配结果；跨帧仅复用像素完全一致的小区域 OCR。跨帧缓存最多16个区域、单区域最多512 KiB，任何像素变化都会重新识别，避免旧识别结果导致误点。

## GPU 与 CPU

文字检测和文字识别使用原来的 PP-OCRv3 模型及前后处理，选择 ONNX Runtime CUDA 后端；OpenCV 的模板、轮廓和颜色处理仍使用 CPU。每个 OCR 会话使用2个 CPU 工作线程，关闭线程空转，OpenCV也限制为2线程，避免两台模拟器各自争抢全部核心。

GPU不可用时保留 CPU 后端。CUDA每个会话的内存池限额为256 MiB，实际总显存还包含模型、CUDA上下文、动态库等，不应把内存池限额理解为整个进程显存上限。默认禁用 TF32，保持原模型精度。

本机可选 GPU 依赖安装在包内 `runtime/gpu`，通过包内 Python 的 `du_gpu_runtime.pth` 启用，原 CPU 安装保留。未修改系统 Python、显卡驱动或系统 CUDA 安装。使用 `requirements-gpu.txt` 固定版本；重新安装时应保持隔离目录并用现有基础依赖，避免顺带升级 NumPy 等组件。

如需回退，可在启动该包的 PowerShell 会话中设置 `$env:SRC_OCR_CPU_ONLY = '1'`，然后重启对应脚本。启动日志的 `OCR det runtime` / `OCR rec runtime` 显示实际启用的后端。

## 本机验证（2026-10-11）

RTX 4070 Laptop，i9-14900HX，两个模拟器运行。同图对照：原祝福页约2.64s；仅限制 CPU 线程约1.54s；GPU与区域精简后，祝福约0.60s、奇迹约0.96s、入口约0.59s、奖励关闭约0.27s、常见结算约0.56s、结束确认约0.54s、近处门识别约0.36s。测试每轮清空识别缓存，未把重复图片缓存命中冒充新画面识别速度。

这些是已保存实机截图的三次预热后中位数，包含该页分类与必要识别，不是所有随机场景的上限。首次模型加载、首次 CUDA 算子执行、游戏动画、战斗、过场加载、两帧稳定确认，不能算作一次 OCR 的耗时。远门多尺度搜索、未知页面回退仍可能超过1s；不以降低识别阈值或裁掉可能目标换取表面速度。

生产选牌日志增加 `detection=...s`，记录真实截图轮询到卡片内容稳定的时间，包括等待动画；与单帧识别指标分开核对。

## 整轮时延优化中的模型输入修正

后续对正在运行的进程采样发现，上层虽然已经裁剪 ROI，`pponnxcr 2.0` 的检测预处理仍将每个区域补到960×960。这使小按钮也进行了大图归一化和卷积计算。

现在只在动态尺寸检测模型上替换补边步骤：保持原缩放比例和坐标变换，按32像素步长对齐，并保留64像素黑色边缘上下文。确认按钮实例的实际检测输入为384×160，卡名条为960×128。不额外压低分辨率或降低识别阈值。只做最小对齐曾导致真实卡名漏一个字，因此保留了经回放验证的边缘上下文。

CUDA识字模型对很窄的输入效率较低，现在将原生规范化结果右侧补零到模型原有的320像素宽度；已有字符像素逐字节保持一致。仍使用原生单张批次，不采用超出显存池限制的批量推理。CPU回退保持原来的识字尺寸。

入口页面在确认类型后直接处理，模式标题与启动按钮共同确认，只有明确处于错误模式时才返回。已取到的首张选项画面也参与稳定性比较，仍要求另一张真实截图内容一致。完整一轮的性能验收按相邻真实结算之间的时间统计，包含进入、加载、战斗、领奖和结算，不以单帧识别速度代替整轮结果。

完整实机采样结果见[首站速通整轮时延验证](DU_FIRST_STATION_LATENCY.md)。

参考：[ONNX Runtime CUDA 后端](https://onnxruntime.ai/docs/execution-providers/CUDA-ExecutionProvider.html)。

## 2026-10-12 事件牌搜索并行

常见的前三类事件牌仍按原顺序识别。均未命中后，仅把后三类独立模板交给最多3个临时CPU工作线程；它们读取同一帧的灰度缓存，全部完成并退出后才允许下一张截图。模板优先顺序、原区域、61个尺度和阈值保持，游戏控制仍只有原主线程，未额外创建OCR/GPU会话。

单纯将OpenCV内部线程从2调到4/8未得到实质收益，因此该设置保持2。尾部模板并行的交错离线采样中，空画面模板搜索中位1180.09→789.91毫秒，有事件画面189.97→175.26毫秒；正式helper在7张真实图上保持匹配框、来源和分数一致，未修改输入图且调用结束没有遗留线程。该数字仅是事件牌匹配组件，未包含门搜索、OCR、截图、移动或游戏转场，不能代替整关/整局验收。证据在evidence/du-full-v16-20261012-0726下。

## 2026-10-12 事件框局部边缘分析

事件方向计算和未知标题的板框校验现在共享同一帧的局部Canny结果，不再各自转换整张1280×720截图。原有候选宽度上限340px、中心偏差0.3w约束决定候选边缘至标题中心最多272px；在其外保留4px上下文，并将坐标裁到实际图像边界。单个输入最大553×584，标题较低时进一步缩小，原图坐标、Canny阈值、几何与四边覆盖条件不变。

9张真实截图中的7条文字的校验结果、原生投影方向与旧版一致；这些实景没有完整四边正例，另外以明确标注的合成完整框验证正向几何和边界行为，不作为实机成功证据。运行中对标题校验与方向计算复用缓存，同一帧内重复请求不再重跑边缘分析。证据：evidence/du-navigation-20261012-1132/event-roi-check.json。此次未以离线时间宣称整关达标。

同时补入本机确证的精确事件名变体“抹色彩”（OCR漏掉“一抹色彩”的首字）和新DU名称“规划航线”。这两种目标此前因人物遮挡板框而无法经过图形回退；未放宽所有标题的模糊匹配或降低原模板阈值。

## 2026-10-12 导航模板的候选搜索缩图

门和事件牌的密集尺度搜索，对宽高均至少32px的模板改用1/4线性尺寸寻找候选，替代此前1/2尺寸；候选搜索像素数进一步减少到此前的1/4。更小的特征仍沿用原路径。候选通过后，必须回到原始ROI、原模板像素和原尺度做匹配确认，接受阈值不变，坐标仍为1280×720原图坐标，所有局部裁剪均限制在图像内。普通UI与敌人模板不使用此新分支。

20张已保存的真实画面（空视角、事件牌、远门/近门及反例）对照中，旧/新识别的目标类型和坐标全部相同，分数差小于0.0001。门、事件牌与近门三项检测合计的离线中位耗时从1.035s降到0.610s，约减少41%；每个测量都从空的当前帧缓存开始。这是模拟器关闭时的离线CPU耗时，不能代表双开实机时延，更不能替代每关60秒验收。证据：evidence/du-full-optimization-20261012-1644/quarter-verified.json。
